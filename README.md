# EVENTFLOW

**EventFlow — платформа для создания и управления цифровыми продуктами.**

Репозиторий содержит дополнительную проектную, архитектурную и техническую документацию EventFlow. Актуальная утверждённая продуктовая спецификация хранится в основном приватном репозитории приложения.

## Канонические документы

- [Спецификация EventFlow 1.2](https://github.com/PelzA83/EventFlow/blob/main/docs/specifications/EventFlow_Specification_1.2.md) — актуальная утверждённая версия.
- [Реестр спецификаций](https://github.com/PelzA83/EventFlow/blob/main/docs/specifications/README.md) — история версий 1.0, 1.1 и 1.2.
- [Дорожная карта демонстрационных продуктов](https://github.com/PelzA83/EventFlow/blob/main/docs/DEMO_RELEASE_PLAN.md) — текущие этапы и ближайшие действия.
- [Project Status](https://github.com/PelzA83/eventflow-project-hub/blob/main/PROJECT_STATUS.md) — оперативная контрольная точка по Demo, проверкам и ограничениям.

## О проекте

EventFlow развивается как платформа с общей функциональной основой и библиотекой универсальных блоков. На текущем этапе основной практический приоритет — демонстрационные новогодние и свадебные приглашения. Другие цифровые продукты, включая подарочные сертификаты, развиваются на общей основе в соответствии с дорожной картой.

## Текущий технический контекст

- Supabase выбран как целевая backend/database-платформа EventFlow.
- Публичная Demo использует SharedWorker и хранит состояние только в памяти активной сессии; это не постоянное хранилище и не production backend.
- Модель организаций согласована на уровне продуктовой логики; наличие согласованной модели не означает, что соответствующая схема уже развёрнута в рабочей базе.
- RSVP и демонстрационные сценарии развиваются поэтапно. Статус конкретной функции определяется актуальными проверками и Project Status, а не только наличием интерфейса или кода.

## Правила ведения документации

1. Актуальная утверждённая спецификация и её история версий находятся в основном репозитории EventFlow.
2. Этот репозиторий содержит дополнительные материалы и аудиты; устаревшие сводки не должны переопределять канонические документы.
3. Согласованные решения отделяются от предложений и открытых вопросов.
4. Результаты технических проверок сохраняются с указанием охвата и ограничений.
5. Изменения базы данных оформляются отдельными SQL-миграциями; исторические SQL-файлы не запускаются повторно без проверки.
6. Секреты, пароли, токены и персональные данные не публикуются в репозитории.
7. После существенных изменений обновляются соответствующие документы и оперативная контрольная точка.

**Документация должна отражать фактическое состояние проекта, а не только запланированную функциональность.**
