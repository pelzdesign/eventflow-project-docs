
# EVENTFLOW — Аудит RSVP

**Дата аудита:** 10.11.2026  
**Компонент:** публичное приглашение и сбор ответов гостей  
**Платформа:** Supabase  
**Статус:** базовая логика реализована, основные проверки выполнены.

## 1. Назначение RSVP

RSVP позволяет гостям через персональную для группы ссылку:

- просмотреть сведения о мероприятии;
- увидеть состав своей группы;
- подтвердить или отклонить участие;
- оставить общий комментарий.

## 2. Структура данных

Используются четыре основные таблицы:

- `events` — мероприятие;
- `guest_groups` — группа приглашённых;
- `guests` — участники группы;
- `rsvp` — ответы участников.

Каждая группа имеет уникальный `access_token`.

Ответ RSVP привязан к конкретному гостю через `guest_id`.

Для одного гостя допускается одна актуальная запись RSVP благодаря ограничению UNIQUE.

## 3. Получение приглашения

Функция:

`get_invitation(p_token text)`

Проверяет групповой токен и возвращает:

- информацию о мероприятии;
- информацию о группе;
- список гостей группы.

Доступ к приглашению предоставляется только при активном мероприятии.

## 4. Отправка ответов

Функция:

`submit_rsvp(p_token, p_responses, p_comment)`

Основные проверки:

1. Формат входного массива.
2. Наличие ответов.
3. Существование группы и мероприятия.
4. Соответствие токена группе.
5. Статус мероприятия.
6. Срок приёма ответов с учётом часового пояса.
7. Количество переданных ответов.
8. Уникальность гостей в запросе.
9. Принадлежность каждого гостя указанной группе.

После успешной проверки функция обновляет RSVP и соответствующие статусы гостей.

## 5. Защита от некорректных запросов

В функции предусмотрены:

- проверка входных данных;
- блокировка записи мероприятия через `FOR UPDATE`;
- проверка принадлежности гостей группе;
- проверка статуса мероприятия;
- проверка дедлайна;
- ограничение количества ответов.

## 6. Тестирование

Для тестирования предусмотрен файл:

`05_rsvp_tests.sql`

В нём проверяются:

- наличие тестового мероприятия;
- наличие группы и гостей;
- отправка ответов;
- изменение статусов;
- корректность подсчётов.

Тестовые данные создаются через `02_seed_data.sql`.

**Особенность:** повторный запуск seed-файла может создавать дубликаты тестовых данных. Это необходимо учитывать при тестировании.

## 7. Ограничения текущей реализации

- Токен выдаётся на группу, а не индивидуально каждому гостю.
- Комментарий хранится на уровне ответа группы.
- Отдельной системы уведомлений гостей пока нет.
- Организаторский интерфейс управления RSVP должен учитывать будущую модель организаций.
- Дополнительные механизмы защиты от массовых запросов требуют отдельной оценки.

## 8. Архитектурные решения

- Не переписывать работающий RSVP без необходимости.
- Сохранять существующие таблицы и связи.
- Новую модель организаций внедрять миграциями.
- После изменения структуры выполнить регрессионное тестирование.
- Проверять, что существующие приглашения и ответы продолжают работать.

## 9. Вывод

Базовый сценарий RSVP реализован.

Получение приглашения и отправка ответов выполняются через серверные RPC-функции.

Система может использоваться как основа дальнейшей разработки EventFlow.

## 10. Следующие проверки

После следующих существенных изменений необходимо проверить:

- повторную отправку ответов;
- попытку ответа за чужого гостя;
- истечение срока RSVP;
- мероприятие в неактивном статусе;
- некорректный или повторяющийся массив ответов;
- конкурентные запросы;
- сохранность существующих ответов после миграций.
