
# EVENTFLOW — Аудит приложения

**Дата:** 10.11.2026  
**Область:** общая техническая готовность приложения  
**Статус:** базовая техническая основа существует, развитие продолжается.

## 1. Текущая основа

Приложение использует Supabase как backend и базу данных.

Реализована базовая серверная логика:

- получение приглашения;
- проверка группового токена;
- отправка RSVP;
- контроль статуса мероприятия;
- контроль срока приёма ответов.

## 2. Реализованные компоненты

На момент аудита существовали:

- таблицы мероприятий;
- группы приглашённых;
- список гостей;
- хранение ответов RSVP;
- серверные функции получения приглашения и отправки ответов;
- базовые тестовые данные;
- SQL-тестирование RSVP.

## 3. Ограничения текущей архитектуры

Существующая схема ориентирована преимущественно на работу публичного приглашения и сбор ответов гостей.

Пока не реализована полноценная система:

- организаций и их владельцев;
- управления несколькими организациями;
- разграничения доступа организаторов;
- коммерческих прав на публикацию мероприятий;
- полноценной административной панели;
- медиагалереи;
- расширенных интерактивных модулей.

Это не считается дефектом существующей RSVP-системы: перечисленные компоненты относятся к дальнейшему развитию продукта.

## 4. Направление развития

Следующий крупный этап — внедрение модели организаций.

Предусматривается:

- `organizations`;
- `organization_members`;
- связь мероприятий с организациями через `events.organization_id`;
- управление доступом владельцев;
- административное управление статусами организаций.

## 5. Основные требования к дальнейшей разработке

1. Сохранять работающий RSVP.
2. Не допускать потери существующих мероприятий и ответов.
3. Внедрять новые компоненты миграциями.
4. Проектировать доступ с учётом принадлежности данных организации.
5. Не предоставлять прямой доступ к таблицам без обоснованной необходимости.
6. Проверять новые функции до применения в рабочей среде.

## 6. Ограничения достоверности

Этот документ фиксирует общие выводы по технической основе проекта.

Он не является полным аудитом frontend-кода, пользовательских интерфейсов, производительности или всех настроек Supabase.

Такие проверки выполняются отдельно, если соответствующие компоненты входят в объём работ.

## 7. Вывод

Существующая техническая основа подходит для поэтапного развития EventFlow.

Главный принцип дальнейшей работы — расширение существующей системы без необоснованного переписывания работающих компонентов.
