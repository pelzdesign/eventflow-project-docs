
# EVENTFLOW — Аудит RLS и безопасности базы данных

**Дата проверки:** 10.11.2026  
**Платформа:** Supabase / PostgreSQL  
**Статус:** основные проверки выполнены, отдельные вопросы остаются открытыми.

## 1. Область проверки

Проверялись:

- включение RLS на основных таблицах;
- наличие RLS-политик;
- прямые права доступа ролей anon и authenticated;
- права выполнения серверных RPC-функций;
- параметры SECURITY DEFINER;
- владелец функций;
- значение search_path.

## 2. Состояние RLS

На всех четырёх основных таблицах RLS включён:

| Таблица | RLS | FORCE RLS |
|---|---|---|
| events | true | false |
| guest_groups | true | false |
| guests | true | false |
| rsvp | true | false |

Результат проверки `pg_policies`:

`No rows returned`

На момент аудита явных RLS-политик не было.

## 3. Прямые права доступа к таблицам

Первоначально у ролей anon и authenticated отсутствовали прямые права:

- SELECT;
- INSERT;
- UPDATE;
- DELETE.

При этом были обнаружены избыточные привилегии:

- REFERENCES;
- TRIGGER;
- TRUNCATE.

### Выполненное исправление

Было выполнено REVOKE лишних прав.

Контрольная проверка после исправления:

- прямые права на таблицы для проверяемых ролей: `No rows returned`;
- обе RPC-функции сохранили право EXECUTE для anon и authenticated.

**Статус:** исправление выполнено и проверено.

## 4. Проверка RPC-функций

Проверены:

- `public.get_invitation(text)`
- `public.submit_rsvp(text, jsonb, text)`

Результаты:

| Параметр | get_invitation | submit_rsvp |
|---|---|---|
| Owner | postgres | postgres |
| SECURITY DEFINER | true | true |
| search_path | пустой | пустой |
| EXECUTE anon | true | true |
| EXECUTE authenticated | true | true |

Публичный доступ к функциям через роль PUBLIC отозван.

Функции используют явно квалифицированные обращения к объектам схемы `public`.

## 5. Архитектурный принцип доступа

Предусмотренная модель работы:

- прямой доступ anon и authenticated к таблицам закрыт;
- публичные операции с приглашениями и RSVP выполняются через специально предусмотренные RPC-функции;
- серверные функции проверяют входные данные и допустимость операции.

Не добавлять прямые права доступа к таблицам без отдельного архитектурного решения.

## 6. Открытые вопросы

На момент завершения аудита оставались вопросы:

1. Проверка внутренней логики RPC на попытки использования чужих токенов и чужих `guest_id`.
2. Проверка граничных сценариев JSON и некорректных входных данных.
3. Дополнительная проверка эффективных привилегий PostgreSQL.
4. Оценка необходимости FORCE ROW LEVEL SECURITY с учётом архитектуры SECURITY DEFINER.
5. Проверка защиты от злоупотребления публичными RPC.

Результаты этих дополнительных проверок нельзя считать подтверждёнными до отдельной фиксации.

## 7. Вывод

На момент проверки:

- RLS включён на всех четырёх основных таблицах;
- явных RLS-политик нет;
- прямые права anon и authenticated на таблицы отсутствуют;
- избыточные REFERENCES, TRIGGER и TRUNCATE отозваны;
- RPC-функции доступны для предусмотренных ролей;
- обе функции используют SECURITY DEFINER и пустой search_path.

Базовая модель предусматривает выполнение публичных операций через ограниченный набор серверных функций.

## 8. Важное замечание

Аудит отражает состояние на 10.11.2026 и не заменяет проверку после будущих изменений схемы, ролей, функций или политик.

При реализации модели организаций необходимо отдельно спроектировать доступ владельцев к данным своих организаций.
