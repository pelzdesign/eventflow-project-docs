
# EVENTFLOW — Аудит базы данных

**Дата аудита:** 10.11.2026  
**Область проверки:** существующая база Supabase  
**Статус:** базовый аудит завершён

## 1. Объём проверки

Проверялись:

- структура основных таблиц;
- связи между таблицами;
- ограничения и индексы;
- настройки RLS;
- права ролей anon и authenticated;
- серверные функции RPC;
- наличие триггеров;
- базовая логика RSVP.

## 2. Фактическая структура базы

На момент аудита существовали четыре основные таблицы:

| Таблица | Назначение |
|---|---|
| events | Мероприятия |
| guest_groups | Группы приглашённых |
| guests | Гости |
| rsvp | Ответы гостей |

Дополнительные особенности:

- В `events` присутствует поле `rsvp_deadline`.
- Доступ к приглашению осуществляется через групповой `guest_groups.access_token`.
- Индивидуальных токенов гостей нет.
- Таблиц организаций, пользователей EventFlow и ролей организаторов в этой схеме ещё нет.

## 3. Связи и ограничения

Проверены внешние ключи, CHECK, UNIQUE и основные связи таблиц.

Базовая структура связей:

- `guest_groups.event_id` → `events.id`
- `guests.group_id` → `guest_groups.id`
- `rsvp.guest_id` → `guests.id`

Удаление родительских записей предусматривает каскадное удаление связанных данных.

## 4. RLS и права доступа

RLS включён на всех четырёх основных таблицах.

На момент аудита запрос к `pg_policies` не возвращал записей: явных RLS-политик не обнаружено.

Прямые права SELECT, INSERT, UPDATE и DELETE для ролей `anon` и `authenticated` отозваны.

Публичная работа с приглашениями и RSVP организована через серверные RPC-функции с `SECURITY DEFINER`.

**Важное наблюдение:** в результатах проверки прав были обнаружены необычные привилегии `REFERENCES`, `TRIGGER` и `TRUNCATE`. Требуется отдельно проверить эффективные права и необходимость их сохранения.

Не добавлять RLS-политики вслепую: сначала необходимо спроектировать разграничение доступа для новой модели организаций.

## 5. Серверные функции

Проверены две основные функции:

### get_invitation(p_token)

- Получает приглашение по групповому токену.
- Возвращает сведения о мероприятии, группе и гостях.
- Проверяет соответствие токена.
- Возвращает данные только для мероприятия со статусом `active`.

### submit_rsvp(p_token, p_responses, p_comment)

- Проверяет формат массива ответов.
- Находит группу и мероприятие.
- Использует блокировку записи мероприятия `FOR UPDATE`.
- Проверяет статус мероприятия и срок приёма ответов с учётом часового пояса.
- Проверяет принадлежность гостей группе.
- Обновляет ответы RSVP и статус гостей.

Обе функции:

- принадлежат `postgres`;
- используют `SECURITY DEFINER`;
- имеют пустой `search_path`;
- доступны для выполнения ролям `anon` и `authenticated`;
- не доступны через EXECUTE для PUBLIC.

## 6. Триггеры и индексы

Триггеров на четырёх основных таблицах не обнаружено.

Синхронизация статуса гостя с ответом RSVP выполняется непосредственно внутри `submit_rsvp`.

В таблице `rsvp` обнаружен дублирующий индекс `idx_rsvp_guest`.

Дубликат был удалён. Оставлен уникальный индекс `rsvp_guest_id_key`, обеспечивающий ограничение UNIQUE по `guest_id`.

Остальные основные индексы признаны достаточными для текущей базовой схемы.

## 7. Выводы

Базовая RSVP-система реализована и может служить основой дальнейшего развития EventFlow.

Переписывание существующих функций и создание новой базы не требуется.

Расширение необходимо выполнять миграциями с сохранением существующих мероприятий, гостей и ответов RSVP.

## 8. Замечания и открытые вопросы

Не считать следующие вопросы окончательно закрытыми:

1. Дополнительная проверка NULL-значений и граничных сценариев в `submit_rsvp`.
2. Проверка эффективных прав `anon` и `authenticated`, включая `TRUNCATE`, `TRIGGER` и `REFERENCES`.
3. Дополнительная проверка настроек безопасности Supabase.
4. Защита RPC от злоупотреблений и ограничение частоты запросов.
5. Проектирование пользователей, организаций, владельцев и разграничения доступа.
