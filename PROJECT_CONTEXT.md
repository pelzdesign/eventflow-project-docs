
# EVENTFLOW — PROJECT CONTEXT

**Назначение:** краткий актуальный контекст проекта для разработчиков и AI-ассистентов.

**Правило:** при расхождении этого файла с подробной документацией приоритет имеют актуальные согласованные решения и фактическое состояние системы.

## 1. Продукт

EventFlow — сервис цифровых приглашений и впечатлений для мероприятий.

Основные направления:
- создание цифровых приглашений;
- управление мероприятиями и гостями;
- сбор RSVP;
- дополнительные интерактивные модули;
- медиагалерея после мероприятия.

Первый рынок — Россия. В перспективе — страны СНГ.

## 2. Текущая техническая основа

- Backend и база данных: Supabase.
- Авторизация: Supabase Auth.
- Основной планируемый способ входа: номер телефона + SMS OTP.
- Реальный SMS-провайдер пока не выбран.
- DEMO-авторизация не должна пересекаться с реальными аккаунтами и заказами.

## 3. Текущая база данных

Существующие основные таблицы:
- `events`
- `guest_groups`
- `guests`
- `rsvp`

Основные серверные функции:
- `get_invitation(p_token)`
- `submit_rsvp(p_token, p_responses, p_comment)`

Базовая логика RSVP реализована.

Подробности и фактическое состояние схемы фиксируются в `02_architecture` и `04_database`.

## 4. Согласованная модель организаций

- Основная сущность: `organizations`.
- Связь пользователей с организациями: `organization_members`.
- Одно мероприятие принадлежит одной организации через `events.organization_id`.
- Создатель организации автоматически становится владельцем.
- Пользователь может состоять в нескольких организациях.
- Несколько владельцев одной организации разрешены.
- На старте реализуется только роль `owner`.
- Владельцы имеют доступ только к данным своих организаций.
- Удаление другого владельца выполняется через специальную административную процедуру.
- Организации имеют статусы `active`, `restricted`, `blocked`, `archived`.

## 5. Коммерческая модель

- Регистрация и создание организации бесплатны.
- Черновики и DEMO бесплатны.
- Публикация реального мероприятия требует оплаченного права.
- Право расходуется при первой публикации.
- До публикации право резервируется за черновиком и может переноситься.
- После первой публикации перенос запрещён.
- Временное скрытие опубликованного мероприятия не возвращает право.
- Все операции с правами аудируются.

## 6. Принципы проектирования

- Не переписывать работающий RSVP без необходимости.
- Расширять существующую систему постепенно.
- Не реализовывать преждевременно сложные универсальные механизмы.
- Не смешивать согласованные решения с предложениями.
- Учитывать безопасность и разграничение доступа.
- Сначала согласовать архитектуру, затем готовить SQL и выполнять миграции.

## 7. Важные ограничения

- Миграция организаций в Supabase ещё не выполнена.
- До миграции необходимо зафиксировать результаты ранее проведённых аудитов.
- Существующие RLS-политики и фактическое распределение мероприятий должны быть учтены.
- Не запускать SQL-изменения без предварительного согласования.
- Не хранить секреты и персональные данные в GitHub.

## 8. Открытые направления

- Завершение документации текущей базы данных.
- Фиксация результатов предыдущих технических аудитов.
- Подготовка и согласование миграции организаций.
- Выбор SMS-провайдера перед первым реальным заказом.
- Дальнейшая разработка продуктовых модулей и медиагалереи.

## 9. Правило обновления

После каждого существенного согласованного изменения проекта этот файл необходимо проверить и при необходимости обновить.

Дата последнего содержательного обновления и номер версии указываются в истории изменений.

### Правила дальнейшей работы

1. Перед повторным аудитом изучать существующую документацию.
2. Не проводить повторную проверку уже подтверждённых вопросов без причины.
3. Новые результаты проверок фиксировать в GitHub.
4. Исторические SQL-файлы не переписывать.
5. Изменения действующей базы оформлять отдельными миграциями.
6. После согласованных изменений обновлять архитектурную документацию и PROJECT_CONTEXT.md.

**Важно:** сохранённые результаты отражают ранее проведённые проверки. Перед внесением изменений в базу необходимо сверять документацию с её фактическим состоянием в Supabase.
