
# EVENTFLOW — Взаимосвязи данных

**Статус:** исходная структура до внедрения организаций.

## 1. Общая модель

Данные организованы по следующей цепочке:

Мероприятие → Группа приглашённых → Гости → Ответы RSVP.

Одно мероприятие может содержать несколько групп приглашённых.

Одна группа может содержать нескольких гостей.

Каждый гость может иметь не более одной актуальной записи RSVP.

## 2. Связи

| Родительская таблица | Дочерняя таблица | Поле связи |
|---|---|---|
| events | guest_groups | event_id |
| guest_groups | guests | group_id |
| guests | rsvp | guest_id |

## 3. Правила целостности

- Все группы принадлежат существующим мероприятиям.
- Все гости принадлежат существующим группам.
- Все ответы RSVP принадлежат существующим гостям.
- Для одного гостя допускается только одна запись RSVP.
- При удалении родительской записи связанные дочерние записи удаляются каскадно.

## 4. Логика доступа

Публичный доступ к данным приглашения осуществляется через групповой токен.

Токен хранится в `guest_groups.access_token`.

Серверные функции проверяют токен и выполняют предусмотренные операции.

Прямой доступ к таблицам для anon и authenticated закрыт.

## 5. Планируемая модель организаций

После расширения структуры цепочка будет выглядеть так:

Организация → Мероприятие → Группа приглашённых → Гости → RSVP.

Предусматривается:

- одна организация может иметь несколько мероприятий;
- одно мероприятие принадлежит только одной организации;
- одна организация может иметь нескольких владельцев;
- пользователь может состоять в нескольких организациях.

Для реализации будут использоваться:

- `organizations`;
- `organization_members`;
- `events.organization_id`.

## 6. Важное ограничение

Планируемые связи организаций не являются частью действующей базы данных до выполнения и проверки миграции.

При внедрении новой модели необходимо сохранить существующие мероприятия, группы, гостей и ответы RSVP.
