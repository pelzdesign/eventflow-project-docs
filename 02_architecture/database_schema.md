
# EVENTFLOW — Структура базы данных

**Платформа:** Supabase / PostgreSQL  
**Статус:** описание исходной схемы до внедрения модели организаций.  
**Дата фиксации:** 11.11.2026

## 1. Общая структура

Текущая база данных содержит четыре основные таблицы:

- `events` — мероприятия;
- `guest_groups` — группы приглашённых;
- `guests` — гости;
- `rsvp` — ответы гостей.

## 2. Таблицы

### events

Хранит информацию о мероприятиях.

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | Первичный ключ |
| title | TEXT | Название мероприятия |
| event_date | DATE | Дата мероприятия |
| event_time | TIME | Время мероприятия |
| timezone | TEXT | Часовой пояс |
| venue_name | TEXT | Название площадки |
| venue_address | TEXT | Адрес площадки |
| status | TEXT | Статус мероприятия |
| created_at | TIMESTAMPTZ | Дата создания |
| rsvp_deadline | DATE | Срок приёма ответов |

Допустимые статусы: `draft`, `active`, `completed`.

### guest_groups

Хранит группы приглашённых.

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | Первичный ключ |
| event_id | UUID | Ссылка на мероприятие |
| name | TEXT | Название группы |
| access_token | TEXT | Уникальный токен доступа |
| created_at | TIMESTAMPTZ | Дата создания |

Токен генерируется автоматически.

### guests

Хранит участников групп.

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | Первичный ключ |
| group_id | UUID | Ссылка на группу |
| first_name | TEXT | Имя |
| last_name | TEXT | Фамилия |
| role | TEXT | Роль участника |
| rsvp_status | TEXT | Статус ответа |
| created_at | TIMESTAMPTZ | Дата создания |

Допустимые роли: `primary`, `member`.

Допустимые статусы: `pending`, `confirmed`, `declined`.

### rsvp

Хранит ответы гостей.

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | Первичный ключ |
| guest_id | UUID | Ссылка на гостя |
| attendance | TEXT | Ответ об участии |
| comment | TEXT | Комментарий |
| responded_at | TIMESTAMPTZ | Дата ответа |

Допустимые значения `attendance`: `yes`, `no`.

Для `guest_id` установлено ограничение UNIQUE.

## 3. Связи таблиц

- `events.id` → `guest_groups.event_id`
- `guest_groups.id` → `guests.group_id`
- `guests.id` → `rsvp.guest_id`

Связи используют внешние ключи с каскадным удалением.

## 4. Основные серверные функции

- `get_invitation(p_token text)` — получение публичного приглашения.
- `submit_rsvp(p_token text, p_responses jsonb, p_comment text)` — сохранение ответов гостей.

Подробности функций будут зафиксированы отдельно.

## 5. Индексы

Основные индексы:

- `idx_guest_groups_event`
- `idx_guests_group`
- `rsvp_guest_id_key` — уникальный индекс для ограничения UNIQUE.

Ранее существовавший дублирующий индекс `idx_rsvp_guest` был удалён.

## 6. Безопасность

RLS включён на всех четырёх таблицах.

Прямой доступ ролей `anon` и `authenticated` к таблицам закрыт.

Публичные операции выполняются через предусмотренные серверные RPC-функции.

Подробности находятся в `03_audits/rls_security_audit.md`.

## 7. Планируемое расширение

В рамках следующего этапа предусматривается добавление:

- `organizations`;
- `organization_members`;
- `events.organization_id`.

Эти изменения пока не применены.

## 8. Важное примечание

Документ описывает исходную структуру, известную на момент фиксации.

Он не заменяет актуальный SQL-снимок базы данных. После получения и проверки полного снимка фактической схемы этот документ необходимо сверить с ним.
