**Дата актуализации:** 14 ноября 2026 года  
**Назначение:** единая навигация для владельца проекта, разработчиков и AI-ассистентов.  
**Главное правило:** сначала определить вопрос, затем открыть документ-источник именно по этой теме. Не читать все репозитории подряд и не считать копии источниками истины.

## 1. С чего начать

Для быстрого понимания проекта достаточно пройти четыре шага:

1. Открыть [дорожную карту](https://github.com/PelzA83/EventFlow/blob/main/docs/DEMO_RELEASE_PLAN.md) — понять приоритет, график и следующий этап.
2. Открыть [оперативный статус Demo](https://github.com/PelzA83/eventflow-demo/blob/main/docs/PROJECT_STATUS.md) — проверить, что фактически реализовано и протестировано.
3. При необходимости открыть [спецификации](https://github.com/PelzA83/EventFlow/tree/main/docs/specifications) — сверить согласованные требования.
4. По теме задачи перейти в соответствующий раздел этого репозитория: архитектура, аудит, база данных, решения или история.

Не начинать с исторических SQL-файлов, старых аудитов или всей спецификации, если задача этого не требует.

## 5. Принцип приоритета: график выпуска

Главный приоритет — как можно быстрее подготовить и показать два убедительных демонстрационных продукта: сначала новогоднее приглашение, затем свадебное.

Порядок текущего этапа:
1. Навигация по документации и дорожная карта приведены в соответствие 14 ноября 2026 года.
2. Целевой code review каркаса завершён 14 ноября: P0-блокеров по исходному коду не обнаружено; конкретные P1-задачи и браузерные проверки зафиксированы в аудите.
3. Следующий рабочий этап — дизайн шаблонов. Ранее обсуждавшиеся визуальные решения свадебного направления сохраняются как исходная база; не заменять их новой концепцией без причины. Визуальное направление новогоднего шаблона ещё предстоит разработать.
4. Параллельно реализовать только минимальные P1-изменения, необходимые для двух визуально различных шаблонов и корректного свадебного сценария.
5. Проверить и показать новогодний продукт первым, затем свадебный.

Не назначать календарные дедлайны без оценки оставшегося объёма. Сначала зафиксировать короткий список блокеров и оценить их; незначительные улучшения не должны сдвигать показ.

## 6. Как оценивать функциональность перед демонстрацией

Каждую функцию относить к одной из категорий:

- **P0 — блокирует показ:** ломает основной путь организатор → персональная ссылка → гостевое приглашение → RSVP → результат у организатора; приводит к неверным данным; мешает открыть приглашение или делает его непригодным на телефоне.
- **P1 — обязательна для конкретного продукта:** ключевая согласованная особенность, без которой продукт теряет смысл. Для свадебного сценария это персонализация, семейные приглашения с независимыми ответами и демонстрационный QR, отражающий подтвердивших участие.
- **P2 — можно отложить:** не мешает эффектно показать продукт и пройти основной сценарий; улучшает удобство, автоматизацию или полноту редактора.
- **P3 — после демонстраций / production:** постоянное хранилище, рабочая серверная инфраструктура, production-безопасность и коммерческие интеграции, если они не требуются для конкретного оплаченного заказа.

Примеры P2/P3 для текущей Demo: полный редактор содержимого и настроек всех блоков, автоматические индикаторы этапов, QR-подпись и офлайн-проверка, полноценный check-in, расширенная медиагалерея, автоматизация релизов, постоянное хранение и переход на production backend.

Не считать функцию обязательной только потому, что она есть в спецификации, интерфейсе или списке универсальных блоков. Оценивать её по реальному сценарию показа.

- changelog — если произошло значимое изменение.

Публичный Project Hub синхронизировать как краткую навигационную копию. Не создавать одинаковые подробные описания в нескольких местах.

## 8. Ограничения и достоверность

- Публичная Demo использует SharedWorker и временные данные активной сессии; это не постоянное хранилище и не production backend.
- Успешная проверка в одной демонстрационной сессии не доказывает сохранение данных между завершёнными сессиями или независимыми устройствами.
- Наличие функции в коде не означает, что её сценарий протестирован.
- Старые материалы Supabase относятся к прежнему техническому состоянию; перед работой с БД нужно проверять фактическую схему и текущие подключения.
- Исторические SQL-файлы не запускать повторно без отдельной проверки.
- Не изменять архитектуру, БД и согласованные продуктовые решения без необходимого согласования.
